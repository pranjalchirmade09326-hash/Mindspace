# MindSpace — Database Schema Blueprint
## 1. Design decisions and scope

### MindSpace project baseline

| Decision | MindSpace scope |
|---|---|
| Project type | Standalone mental-health and emotional-wellbeing support platform with stepped support |
| Database | PostgreSQL relational database |
| Core modules | MindSpace authentication and roles; consent and privacy requests; chat/voice intake; AI-supported wellbeing; private journaling and self-help activities; mood/check-ins; peer-listener matching and conversations; human-led safety resources and escalation; notifications; workflow orchestration; audit |
| Out of scope | Licensed therapist/provider services, clinical records/EMR, diagnosis, prescriptions, appointments, FHIR exchange, coworking/room booking, workspace subscriptions, and general community forums |

This is a proposed schema for a new, standalone MindSpace system based on the SDD’s two in-scope data domains—Peer Support and Wellbeing—plus independent safety operations and cross-cutting identity, workflow, AI, eventing, and audit capabilities. It prioritizes consent, least-privilege access, auditability, provenance, and explicit boundaries between data domains.

MindSpace owns this schema and its database. It is designed specifically for MindSpace's peer-support-centered wellbeing product, with all MindSpace data, identities, code, and tables defined independently.

- MindSpace authentication is managed by its own BetterAuth configuration. `app_principals.user_id` is the MindSpace identity subject used by MindSpace application records.
- Backend Data Access Layer: The MindSpace backend is implemented in **Python** (using FastAPI, SQLAlchemy 2.0 Async, asyncpg, and Pydantic schemas in `backend/mindspace-fastapi`). The Python backend maps these database entities, executes async transactions, enforces application-level AES-256-GCM encryption, and exposes typed REST and MCP interfaces.
- MindSpace does not include professional clinical interoperability or FHIR resources in the confirmed scope.
- Uses UUIDs for new domain records, `TEXT` for MindSpace-auth subject identifiers, and `TIMESTAMPTZ` for instants.
- Uses separate schemas and database roles as a recommended logical boundary. A separate database/cluster may be required by the privacy/security assessment.
- Stores sensitive message and narrative content as application-encrypted ciphertext (`BYTEA`) and keeps encryption key material outside PostgreSQL. Do not log plaintext or store secrets in JSON.
- Uses JSONB only for bounded, versioned variable payloads; core relations and workflow state remain relational.
- Extends the initial 32-table MindSpace core schema with 16 SDD-driven entities below. The resulting 48-table conceptual inventory is a planning count, not a count of deployed tables or a migration target; tables may be merged or split during technical review if domain ownership and controls remain explicit.

### PostgreSQL conventions

- Enable `pgcrypto` only if database-generated UUIDs use `gen_random_uuid()`. UUIDs may instead be generated by the application.
- Use `TIMESTAMPTZ` in UTC; render in the member’s selected timezone.
- Use `TEXT` plus `CHECK` constraints or PostgreSQL enums for controlled values. For frequently evolving states, prefer text with a check or reference table to simplify rollout.
- Every table should have a primary key. Domain rows should have `created_at`; mutable rows should also have `updated_at`.
- Use `ON DELETE RESTRICT` for sensitive business records and audit history. Prefer deactivation/soft deletion and policy-based purge jobs over cascading deletes.
- `*_ciphertext BYTEA` is ciphertext only; encryption/decryption, key rotation, and access logging are application/security responsibilities.
- `JSONB` fields require schema/version validation at the application boundary.

## 3. Shared identity, consent, and privacy tables

### `app_principals`

MindSpace-local application principal mapped to the user identity managed by MindSpace's BetterAuth configuration. Authentication credentials and sessions remain in the MindSpace auth subsystem; no other project's identity is imported or shared.

| Field | PostgreSQL type | Constraints | Description |
|---|---|---|---|
| `user_id` | `TEXT` | PK, NOT NULL | Stable MindSpace authentication subject identifier |
| `account_state` | `TEXT` | NOT NULL, DEFAULT `'active'`, CHECK | MindSpace account access state |
| `created_at` | `TIMESTAMPTZ` | NOT NULL, DEFAULT `now()` | First seen by MindSpace |
| `updated_at` | `TIMESTAMPTZ` | NOT NULL, DEFAULT `now()` | Last local state change |
| `deactivated_at` | `TIMESTAMPTZ` | NULL | Local deactivation time |

## 9. Deletion, retention, and referential integrity

- **MindSpace principal:** Do not cascade delete. Deactivate the MindSpace account; coordinate authentication identity deletion with MindSpace's own identity provider.
- **Consent, audit events, and safety actions:** Append-only or restricted updates; retain according to legal and operational policy.
- **Intake, journals, messages, AI sessions:** Soft-delete/mark for deletion first, then execute a policy-controlled purge or cryptographic erasure process. Preserve required audit evidence without retaining unnecessary content.
- **Dependent child rows:** Use `RESTRICT` for sensitive records. `CASCADE` may be used only inside a controlled, tested purge transaction after policy approval; avoid user-triggered cascades that erase audit/evidence or break references.
- **Published content and listener eligibility/training records:** Use status/expiry fields rather than deleting records referenced by history.
- **Polymorphic source references** such as `source_record_id` cannot be enforced by a standard FK. Validate in the service layer, restrict allowed types, and log changes.
- Retention durations, legal holds, deletion exceptions, backups expiry, and encryption-key destruction are unresolved business/legal decisions; do not invent them in schema defaults.

## 10. Database-level security and privacy controls

1. **Credential security:** MindSpace's BetterAuth configuration owns password hashing and authentication secrets. Never store plaintext passwords, reset tokens, API keys, or provider secrets in this schema.
2. **Least privilege:** Use separate database roles for app runtime, migration, reporting, and break-glass administration. Runtime should not own tables or run DDL.
3. **Record separation:** Prefer separate PostgreSQL schemas and grants for member wellbeing, peer support, safety, and operational data. If a single runtime credential can read every schema, the logical boundary is not effective.
4. **Row-level security:** Consider PostgreSQL RLS as defense in depth after correctly setting authenticated identity context transactionally. RLS does not replace server-side authorization and can be bypassed by privileged owners.
5. **Application encryption:** Encrypt sensitive narrative at the application boundary with managed keys, rotation, and audited access. `BYTEA` ciphertext does not itself provide encryption.
6. **Minimize indexes on sensitive identifiers:** Use keyed HMACs for lookup where required; avoid plain hashes of predictable government/license identifiers.
7. **No sensitive logs:** Exclude message bodies, intake answers, journal content, tokens, and raw AI prompts from SQL logs, traces, and audit metadata.
8. **Separate environments:** Synthetic data only in local/dev/test. Production secrets, databases, and encryption keys must be isolated.
9. **Backups and restore:** Encrypt backups, restrict access, test restores, and align backup expiry with deletion/retention policy.
10. **Audit is tamper-resistant operationally:** Append-only database permissions, restricted readers, external protected log shipping where required, and monitored administrative access.
11. **Transactions and concurrency:** Use transactions for consent and sharing, match acceptance, workflow task assignment, and safety assignment. Enforce uniqueness/state transitions in the database where possible.
12. **No unauthorized data propagation:** Do not replicate sensitive fields into analytics, search, or AI systems without explicit purpose, consent, and retention controls.

## 11. Standalone project boundary and selective intake inspiration

MindSpace is a new application with its own identity configuration, PostgreSQL database, schema, API, source code, and operational environment. This blueprint defines MindSpace's entities from its own requirements; it does not depend on another project's tables or services.

Intake may use familiar patterns such as conversational chat/voice and resumable answers. MindSpace defines its own questions, consent, response fields, safety behavior, validation, and data lifecycle. Product inspiration does not imply copying source code, table definitions, accounts, credentials, content, or stored records.

Other product capabilities—authentication, peer support, wellbeing, safety, AI orchestration, and workflows—are designed as MindSpace-owned components. The project does not depend on or import another application's code, identity, database, or services.

No cross-project data migration is in scope. If a separate, explicitly authorized migration is ever requested, it requires its own legal basis, consent/notice, field-level mapping, access controls, retention policy, test plan, reconciliation, and approval before any records move.

## 15. Implementation and governance notes

- Clinical records, licensed-provider workflows, and FHIR integration are out of scope for the confirmed peer-support and wellbeing release.
